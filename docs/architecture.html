Architecture · docker compose

Claude Code 利用状況
収集サーバーの構成案

Claude Code が OTLP で送るメトリクスとイベントを、docker compose で立てたサーバーで受けて保存・可視化する。5 つの構成案を比べ、段階的に導入する進め方を提案する。

2026-10-12対象：Claude Code v2.1.2xx 系の OTel 出力taskapp OTEL-1

Summary

結論：Collector を中心に置き、バックエンドを段階的に足す

推奨する進め方

  1. PoC：案 C（grafana/otel-lgtm 1 コンテナ）で、データの中身とダッシュボードを試す。
  2. 本番の基本形：案 B（Collector + Prometheus + Loki + Grafana）。前段に Caddy（TLS）を置き、Bearer トークンで認証する。
  3. 監査用：案 A の file exporter を Collector に足し、JSONL も残す（1 行の追加で済む）。
  4. 長期分析：人数が増えた、または人事・組織データと結合したくなったら、案 D（ClickHouse）を追加する。
どの案でも Claude Code → OTel Collector は同じ。保存先は Collector の exporter を足すか差し替えるだけなので、クライアント設定（managed settings）は最初の 1 回だけ配ればよい。

サーバー側で決めること

  • 入口：TLS 終端と認証（Bearer / mTLS）
  • プロトコル：http/protobuf を推奨（トークン更新スクリプトが使える）
  • メトリクスの集計方式：クライアントは既定の delta のまま、Prometheus 向けには Collector で cumulative に変換
  • 機密度：OTEL_LOG_TOOL_DETAILS などの詳細データを受けるか、受けるなら Collector で何を消すか
  • 保持期間：メトリクス・イベント・監査ログそれぞれ
  • カーディナリティ：session.id をメトリクスに載せるか

クライアント側の設定・属性・イベントの詳細は既存資料「Claude Code × OpenTelemetry — 利用状況モニタリング」を参照。本資料はサーバー側の設計に絞る。

1. 前提

サーバーが受けるもの：3 つのシグナル

メトリクス metrics

8 種のカウンター。セッション数、コード行数、PR・コミット数、コスト、トークン、編集ツールの許可判断、アクティブ時間。

既定の送信間隔 60 秒。集計方式は既定で delta。

置き場所の候補：Prometheus / Mimir / ClickHouse

イベント logs

1 件ずつの出来事。user_prompt、api_request（cost_usd 付き）、tool_decision と tool_result、skill_activated など 20 種以上。

既定の送信間隔 5 秒。claude -p 1 回で約 50 件出た実測あり。

置き場所の候補：Loki / ClickHouse / JSONL ファイル

トレース traces · beta

interaction → llm_request / tool のスパン。待ち時間の内訳が分かる。

有効化には CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1 が必要。

置き場所の候補：Tempo / ClickHouse。初期は対象外にして、受け口だけ用意しておく。

用途ごとに必要なシグナル

用途主に使うシグナルストレージに求めること
コスト・トークンのダッシュボードメトリクス（または api_request イベント）時系列の集計が速い
利用実態（誰が・どの repo で・どの Skill を）イベント属性で絞り込み・集計できる
監査（どんなコマンドを実行したか）イベント（tool_result + OTEL_LOG_TOOL_DETAILS）改ざんされにくく、長く残る
月次レポート・人事データとの結合イベント + メトリクスSQL で JOIN できる、年単位で保持

# otel-collector.yaml（案 A の要点）
exporters:
  file/audit:
    path: /data/audit.jsonl
    format: json
    rotation:
      max_megabytes: 100
      max_days: 365      # 記事にはなかった保持期間
      max_backups: 500
      localtime: true
service:
  pipelines:
    logs:    { receivers: [otlp], processors: [memory_limiter, batch], exporters: [file/audit] }
    metrics: { receivers: [otlp], processors: [memory_limiter, batch], exporters: [file/audit] }

# 調べ方：あるセッションで実行された Bash コマンド
jq -c '.resourceLogs[].scopeLogs[].logRecords[]
  | select(.attributes[]? | .key=="tool_name" and .value.stringValue=="Bash")' audit.jsonl
  • コンテナ 1 つ、メモリ 100 MB 程度。数分で立つ。
  • 全属性がそのまま残る。後から別のストレージに読み込み直せる（生データの保管庫になる）。
  • 監査用途では「加工しない原本」があること自体に価値がある。
  • ダッシュボードがない。集計は毎回 jq を書く。
  • ファイルが大きくなると検索が遅い。
  • 改ざん対策は別に必要（追記専用の権限、定期的に外部へ退避、ハッシュの記録）。
向いている場面：個人・少人数での監査、案 B / D の「並走する原本」。

イベントは Loki のネイティブ OTLP 受信へ

  • 参考記事が多く、ダッシュボードの例がそのまま使える。
  • メトリクスとログを Grafana の 1 画面で並べられる。prompt.id でやり取りを追える（FLINTERS のデモ）。

  • PromQL / LogQL は JOIN が苦手。「部署別の月次コスト」のような集計は工夫が必要。
  • ラベルの数（カーディナリティ）を気にする必要がある。
向いている場面：チーム〜数十名。リアルタイムのダッシュボードとアラートが主な目的。

3. 構成案 B

案 B の compose と Collector 設定（要点）

# compose.yaml（抜粋。バージョンは .env で固定）
services:
  caddy:
    image: caddy:${CADDY_VERSION}
    ports: ["443:443"]
    volumes: [./caddy/Caddyfile:/etc/caddy/Caddyfile:ro]
  collector:
    image: otel/opentelemetry-collector-contrib:${OTELCOL_VERSION}
    command: ["--config=/etc/otelcol/config.yaml"]
    environment:
      OTEL_INGEST_TOKEN: ${OTEL_INGEST_TOKEN}
    volumes: [./collector/config.yaml:/etc/otelcol/config.yaml:ro]
    depends_on: [prometheus, loki]  # push 先が先に起動
  prometheus:
    image: prom/prometheus:${PROMETHEUS_VERSION}
    command:
      - --config.file=/etc/prometheus/prometheus.yml
      - --web.enable-otlp-receiver
      - --storage.tsdb.retention.time=400d
    volumes: [prom-data:/prometheus, ...]
  loki:
    image: grafana/loki:${LOKI_VERSION}
    volumes: [loki-data:/loki, ...]
  grafana:
    image: grafana/grafana:${GRAFANA_VERSION}
    environment:
      GF_SECURITY_ADMIN_PASSWORD__FILE: /run/secrets/gf_admin
    volumes: [./grafana/provisioning:/etc/grafana/provisioning:ro]
volumes: { prom-data: {}, loki-data: {}, grafana-data: {} }
# collector/config.yaml（抜粋）
extensions:
  health_check: {}
  bearertokenauth:
    token: ${env:OTEL_INGEST_TOKEN}
receivers:
  otlp:
    protocols:
      http:
        endpoint: 0.0.0.0:4318
        auth: { authenticator: bearertokenauth }
processors:
  memory_limiter: { check_interval: 5s, limit_mib: 512 }
  batch: {}
exporters:
  otlp_http/prometheus:
    endpoint: http://prometheus:9090/api/v1/otlp
  otlp_http/loki:
    endpoint: http://loki:3100/otlp
service:
  extensions: [health_check, bearertokenauth]
  pipelines:
    metrics:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [otlp_http/prometheus]
    logs:
      receivers: [otlp]
      processors: [memory_limiter, transform, batch]
      exporters: [otlp_http/loki]  # + file/audit で案 A 併用

Prometheus の OTLP 受信フラグとパス、Loki の /otlp は v3 系の仕様。採用するバージョンのドキュメントで最終確認すること。

3. 構成案 B

案 B のダッシュボード：PromQL と LogQL の例

メトリクス（Prometheus）

# モデル別のコスト（直近 24h）
sum by (model) (increase(claude_code_cost_usage_USD_total[24h] anchored))

# 利用者別のコスト（今月）
sum by (user_email) (increase(claude_code_cost_usage_USD_total[30d] anchored))

# トークン種別
sum by (type) (rate(claude_code_token_usage_tokens_total[1h]))

# 人の操作時間 vs CLI の稼働時間
sum by (type) (increase(claude_code_active_time_seconds_total[1d] anchored))

anchored（外挿しない increase）と、開始時刻に 0 を入れる機能は Prometheus 3.x の実験的機能（--enable-feature=promql-extended-range-selectors,created-timestamp-zero-ingestion）。短いセッションはカウンターを 1 回しか送らないため、両方ないと値が出ないか膨らむ（実測）。

イベント（Loki）

# Skill の発動回数：利用者 × リポジトリ × Skill
sum by (user_email, vcs_repository_name, skill_name) (
  count_over_time(
    {service_name="claude-code"}
      | event_name="skill_activated" [7d]))

# 拒否されたツール実行
{service_name="claude-code"}
  | event_name="tool_decision" | decision="reject"

# 1 回のやり取りをたどる
{service_name="claude-code"} | prompt_id="5d3b856f-..."
Grafana のダッシュボードとデータソースは grafana/provisioning/ にファイルで置き、リポジトリで管理する（手で作った画面は消えやすい）。

名前の変換例は Qiita @ysit（claude_code_cost_usage_USD_total）。Loki の structured metadata ではドットがアンダースコアに置き換わる。

3. 構成案 D

案 D の分析クエリ例

-- 利用者 × 月 のコストとリクエスト数
SELECT
  toStartOfMonth(Timestamp)               AS month,
  LogAttributes['user.email']              AS user,
  round(sum(toFloat64OrZero(
    LogAttributes['cost_usd'])), 2)        AS cost_usd,
  count()                                  AS requests
FROM otel.otel_logs
WHERE LogAttributes['event.name'] = 'api_request'
GROUP BY month, user
ORDER BY month, cost_usd DESC;

-- 部署別（組織マスタと JOIN）
SELECT o.department, round(sum(toFloat64OrZero(
         l.LogAttributes['cost_usd'])), 2) AS cost
FROM otel.otel_logs l
JOIN org.members o ON o.email = l.LogAttributes['user.email']
WHERE l.LogAttributes['event.name'] = 'api_request'
  AND l.Timestamp >= toStartOfMonth(now())
GROUP BY o.department;
-- Skill の発動：誰が × どの repo で × どの Skill を
SELECT
  LogAttributes['user.email']           AS user,
  LogAttributes['vcs.repository.name']  AS repo,
  LogAttributes['skill.name']           AS skill,
  LogAttributes['invocation_trigger']   AS trigger,
  count() AS n
FROM otel.otel_logs
WHERE LogAttributes['event.name'] = 'skill_activated'
GROUP BY user, repo, skill, trigger
ORDER BY n DESC;

-- 監査：今週実行された Bash コマンド
SELECT Timestamp, LogAttributes['user.email'],
       LogAttributes['tool_parameters']
FROM otel.otel_logs
WHERE LogAttributes['event.name'] = 'tool_result'
  AND LogAttributes['tool_name'] = 'Bash'
  AND Timestamp >= now() - INTERVAL 7 DAY;
頻繁に使う属性（user.email、event.name など）は、ClickHouse のマテリアライズドビューで列に切り出すと速くなる。vcs.* はクライアントで OTEL_METRICS_INCLUDE_REPOSITORY=true、tool_parameters は OTEL_LOG_TOOL_DETAILS=1 が前提。

3. 構成案 E

案 E：OSS の統合監視製品を使う

SigNoz

OTel ネイティブの APM。中身は OTel Collector ＋ ClickHouse ＋ 独自 UI。公式リポジトリに docker compose が同梱されている。

  • ログ・メトリクス・トレースを 1 つの UI で検索できる。アラートもある。
  • 保存先が ClickHouse なので、案 D と同じく SQL も使える。
  • コンテナ数が多く、メモリは 4 GB 以上を見込む。
  • UI とスキーマが製品に依存。バージョンアップに追従が必要。

OpenObserve

単一バイナリの軽量な監視基盤。OTLP を直接受け、ローカルディスクかオブジェクトストレージに保存する。

  • コンテナ 1 つで、ログ・メトリクス・トレースと UI がそろう。
  • SQL ライクな検索ができる。保存の圧縮率が高い。
  • Grafana ほど情報が多くない。ダッシュボードの例を自作する必要がある。
  • ライセンス条件（AGPL など）を採用前に確認する。
判断のポイント：既製の UI で「すぐに検索・アラートしたい」なら E。「Claude Code 専用のダッシュボードやレポートを作り込みたい」なら B / D の方が自由度が高い。どちらでも Collector を前段に置いておけば、後で乗り換えられる。

製品の構成・要件は各製品のドキュメントで最新を確認すること。

5. 推奨

推奨：段階的に導入する

Step 1

PoC（案 C）

自分の端末だけ ~/.claude/settings.json で送る。何が取れるか、どのダッシュボードが欲しいかを決める。

期間の目安：1〜2 日

Step 2

本番の基本形（案 B）

Caddy + 認証付き Collector + Prometheus + Loki + Grafana。Step 1 のダッシュボードを provisioning に移す。

期間の目安：1 週間

Step 3

監査の原本（＋案 A）

logs パイプラインに file/audit を追加。日次で別ホストへ退避し、ハッシュを記録する。

詳細ログを受ける方針が決まってから

Step 4

長期分析（＋案 D）

利用者が増えた・月次レポートや組織データとの結合が必要になったら ClickHouse を追加。必要なら Loki を縮退させる。

目安：数十名を超えたら

この順にする理由

  • Collector が全案の共通部品なので、後から exporter を足すだけで拡張できる。手戻りがない。
  • クライアント設定（送信先・トークン）は Step 2 で 1 回配れば、Step 3・4 で変えなくてよい。
  • 最初から ClickHouse にすると、何を分析したいか決まる前に運用負荷を抱える。

Step 2 の時点で決めておく

  • 受けるデータの範囲（OTEL_LOG_TOOL_DETAILS などの詳細ログを受けるか）
  • 保持期間（メトリクス 13 か月、イベント 90 日、監査 1 年 など）
  • 閲覧できる人（Grafana の権限、個人単位のコストを誰が見るか）

認証の選択肢

方式サーバー側評価
静的 Bearerbearertokenauth 拡張最も簡単。トークンが全端末に配られる点は割り切り（ZOZO の方式）
otelHeadersHelper同上（短命トークンを検証）29 分ごとに再取得できる。http 系のみ（grpc 不可）

Grafana と Collector の受信ポート（4317 / 4318）は外に開かず、入口（:443）だけを公開する。自宅や社内 LAN だけで使う場合も、トークンは入れておく（設定を後から変えずに済む）。

6. 共通設計

Collector のパイプライン：受けてから何をするか

otlp
receiver
+ bearertokenauth
→
memory_limiter
過負荷時に受信を絞る（最初に置く）
→
transform
resource 属性をログ属性にコピー（ZOZO の教訓）
→
attributes / redaction
保存先ごとに機密項目を削除・ハッシュ化
→
batch
まとめて送る（最後に置く）
# resource 属性（OTEL_RESOURCE_ATTRIBUTES の department など）を
# ログ属性にもコピーする
transform/copy_resource:
  log_statements:
    - context: log
      statements:
        - set(attributes["department"], resource.attributes["department"])
        - set(attributes["team.id"], resource.attributes["team.id"])

# ダッシュボード用には詳細を落とす（監査用の file には落とさない）
attributes/strip_details:
  actions:
    - { key: tool_parameters, action: delete }
    - { key: tool_input,      action: delete }
    - { key: prompt,          action: delete }
    - { key: user.email,      action: hash }  # 匿名化する場合

保存先ごとにパイプラインを分ける

logs/dashboard:
  processors: [memory_limiter, transform/copy_resource,
               attributes/strip_details, batch]
  exporters:  [otlp_http/loki]
logs/audit:
  processors: [memory_limiter, transform/copy_resource, batch]
  exporters:  [file/audit]

同じ receiver を 2 つのパイプラインで共有できる。見せる用と保管用で機密度を変える。

セットアップ中は debug exporter を足して中身を確認し、本番では外す（Qiita の教訓）。Collector 自身のメトリクス（:8888）も Prometheus で取る。

6. 共通設計

メトリクスの集計方式とカーディナリティ

delta と cumulative

Claude Code は既定で delta（前回送信からの増分）を送る。Prometheus は cumulative（累計）前提なので、どこかで変換が必要。

  1. 採用 Collector の delta_to_cumulative：クライアントは既定の delta のままで、3 案とも同じ設定を配れる。状態をメモリに持つので Collector は 1 台にする。
  2. クライアントで cumulative を指定（…_TEMPORALITY_PREFERENCE=cumulative）：案 D・D′ で値を単純に合計できなくなるので使わない。
  3. scrape 方式（prometheus exporter）：exporter 側で累積する。delta の扱いは採用バージョンで確認する。
  4. 案 D：api_request イベントの cost_usd で集計すれば、メトリクスを使わないので影響しない。

カーディナリティ（案 B で重要）

クライアント側の変数推奨
OTEL_METRICS_INCLUDE_SESSION_ID既定（true）のまま。false にするとイベントからも消える（実測）。案 B は Collector でメトリクスからだけ外す
OTEL_METRICS_INCLUDE_ACCOUNT_UUIDtrue（利用者別コストに必要）
OTEL_METRICS_INCLUDE_VERSIONtrue（バージョン別に見る）
OTEL_METRICS_INCLUDE_REPOSITORYtrue（repo 別に見る。イベントにも付く）

セッション単位の分析はイベント（Loki / ClickHouse）側で行う。

間欠的な利用への対応

Claude Code は使うときだけ送る。scrape 方式では metric_expiration を長め（例 180m）にしないと、系列が途中で消えて increase() がずれる（Qiita の教訓）。

出典 monitoring-usage（Metrics temporality / cardinality control）・Qiita @ysit

7. クライアント

クライアント側：サーバーに合わせて配る設定

// deploy/common/client/settings.json（組織では managed settings で配布）
{
  "env": {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
    "OTEL_METRICS_EXPORTER": "otlp",      // managed に書くと止められない
    "OTEL_LOGS_EXPORTER": "otlp",
    "OTEL_EXPORTER_OTLP_PROTOCOL": "http/protobuf",
    "OTEL_EXPORTER_OTLP_ENDPOINT": "https://otel.example.internal",
    "OTEL_EXPORTER_OTLP_HEADERS": "Authorization=Bearer xxxxx",
    "OTEL_METRICS_INCLUDE_VERSION": "true",
    "OTEL_METRICS_INCLUDE_REPOSITORY": "true"
    // 監査が必要なら追加："OTEL_LOG_TOOL_DETAILS": "1"
  }
}

置き場所

  • 組織：managed settings（macOS は /Library/Application Support/ClaudeCode/）を MDM で配る。送信先がロックされ、利用者が変えられない。
  • 個人・PoC：~/.claude/settings.json の env。
  • リポジトリの .claude/settings.json は不可：OTel の送信先は無視される。repo の区別は vcs.* 属性で行う。
API キー・Bedrock・Vertex で使う場合は user.email が付かない。OTEL_RESOURCE_ATTRIBUTES で利用者 ID を足し、サーバー側の transform でログ属性にコピーする。
OTEL_LOG_TOOL_DETAILS を有効にすると Bash コマンドやファイルパスが届く。サーバーの閲覧権限とバックアップ先が、その機密度に耐えるかを先に決める。

詳細は既存資料「Claude Code × OpenTelemetry — 利用状況モニタリング」（設定・属性・イベント）と monitoring-usage を参照。
